# FranchiseFlow 产品化设计

## 目标

把当前的门店招牌替换 Demo 推进成一个可持续迭代的产品原型：用户上传一条连续门店视频和任意数量的分店素材，系统自动发现可替换的平面招牌，验证候选区域，跟踪镜头运动，并生成浏览器可播放的分店视频。

产品愿景面向任意连锁品牌。第一版支持范围限定为：单条连续镜头、一个主要平面招牌、720p 视频、15 秒以内、1 到 10 个分店素材。出现镜头切换、多个候选平面、前景遮挡或模型低置信度时，系统进入人工确认流程。

## 当前证据与约束

- `spikes/franchiseflow/tracker.py` 已经能用 SIFT、RANSAC 和 LK 处理给定四角的平面跟踪。
- H.264、`yuv420p`、`faststart` 转码已经接入，输出可以通过 Flask 的 Range 响应播放和拖动。
- 当前视觉模型在倾斜商业立面上可能把砖墙、窗户和门洞混入四边形，人工 `quad.json` 仍是可靠基线。
- 当前 6 秒 144 帧基线运行约 122 秒，其中纯跟踪约 63 秒；输出没有原音频。
- 当前 Web 请求同步阻塞，样片目录和 `demo_cut.mp4` 仍被忽略，干净克隆后不能直接获得预置样片。
- API 密钥只允许从环境变量或被忽略的 `.env` 读取，模型响应、日志、截图和 Git 历史不得包含密钥。

## 用户流程

1. 用户上传一个 MP4 视频和 1 到 10 张分店招牌图片。
2. 系统检查视频是否为单条连续镜头，并抽取首帧、中间帧和末帧。
3. 视觉模型在三帧组成的输入中提出一个或多个候选招牌平面，返回归一化四角、置信度、模型名和原因。
4. 本地验证器检查候选四角的凸性、面积、图像边界、招牌区域纹理点数量，以及三帧之间的平面变化是否合理。
5. 验证通过时进入自动跟踪；验证失败时显示候选预览和失败原因，用户可以拖动四角完成一次人工确认。
6. 跟踪器对每帧估计平面变换。SIFT/RANSAC 为主要路径，LK 双向光流用于短暂特征失效，无法验证的帧保留原画并写入失败记录。
7. 合成器将每个分店素材透视变换到同一组每帧四角，保留输入视频音频，并通过 FFmpeg 输出 H.264、`yuv420p`、`faststart` MP4。
8. 页面展示任务状态、初始化来源、候选预览、失败帧、处理耗时和所有分店输出链接。

## 组件与接口

### 视觉定位

`VisionClient.locate_candidates(image_bytes, width, height, target_hint=None) -> dict`

返回结构：

```json
{
  "model": "gemini-3.1-flash-image",
  "candidates": [
    {
      "quad": [[0.1, 0.1], [0.8, 0.1], [0.8, 0.3], [0.1, 0.3]],
      "confidence": 0.82,
      "reason": "..."
    }
  ]
}
```

坐标只接受 `[0, 1]` 归一化值或完整像素坐标，禁止混用。模型输出必须经过 JSON、有限数值、凸四边形、面积和边界校验。模型失败、响应异常或候选为空时，任务状态为 `vision_failed`，不能自动猜测矩形。

### 候选验证

`validate_candidate(video_samples, candidate) -> ValidationResult`

验证结果至少包含：

- `accepted: bool`
- `reasons: list[str]`
- `sample_metrics`: 每个采样帧的面积、边界、纹理特征点和投影变化
- `requires_human_review: bool`

验证器只负责判断候选是否满足跟踪前提，不把重投影拟合残差当作真实物理边界误差。

### 跟踪与合成

保留现有接口并扩展：

`run_tracker(video, quad, signs, out_dir, initialization_mode, preserve_audio=True) -> summary`

其中：

- `initialization_mode` 只能是 `vision_model`、`manual_fallback` 或 `reviewed_candidate`。
- `signs` 长度为 1 到 10。
- `summary` 必须记录输入视频、分支数量、初始化来源、模型名、帧数、失败帧、处理耗时、编码格式和音频策略。
- 失败帧不得沿用上一帧的替换画面。

### 任务 API

当前同步接口改为本地可复现的轻量任务状态：

- `POST /api/jobs` 创建任务并返回 `job_id`。
- `GET /api/jobs/<job_id>` 返回 `queued`、`running`、`needs_review`、`completed`、`failed` 或 `vision_failed`。
- `POST /api/jobs/<job_id>/review` 提交用户确认后的四角。
- `GET /api/jobs/<job_id>/outputs` 返回每个分店的 H.264 视频链接。
- 旧的 `POST /api/render` 保留为兼容入口，内部转发到任务创建流程。

任务状态和结果使用每个任务目录下的 JSON 文件保存，不引入数据库。处理线程在本地运行，避免一次请求占满浏览器连接。

## 数据和安全

每个任务目录包含：

- `manifest.json`：输入文件名、分店名、初始化来源、模型名和版本。
- `samples/`：首帧、中间帧和末帧候选预览。
- `tracking.jsonl`：逐帧状态和指标。
- `summary.json`：最终统计。
- `outputs/`：分店视频。

上传文件名必须经过安全化处理。输出路径只能从任务目录提供。上传大小、视频时长和分支数量需要有上限。所有任务目录、原始上传、生成视频和 `.env` 保持 Git 忽略。

## 失败策略

- API 401、403、超时、响应结构错误：任务进入 `vision_failed`，返回可读错误，不创建伪造结果。
- 候选四角不合法或三帧验证不一致：任务进入 `needs_review`。
- 人工确认后仍无法建立稳定单应矩阵：任务进入 `failed`，保留原始帧记录。
- 单帧跟踪失败：写入失败帧，输出原画帧，继续处理后续帧。
- FFmpeg 不存在或转码失败：任务在进入长时间处理前失败，并说明安装要求。
- 发生前景遮挡：当前版本记录为已知限制，不声称具备遮挡抠像能力。

## 验收标准

### 自动定位

- 正确候选能通过三帧验证并进入 `vision_model`。
- 已知错误候选四角会进入 `needs_review`，不会生成自动成功结果。
- 人工修正后的任务状态为 `reviewed_candidate`，审计记录保留原候选和修正后的四角。

### 视频生产

- 1、3、10 个分支素材都能生成对应数量的视频。
- 所有输出为 H.264、`yuv420p`、`faststart`，浏览器支持 Range 播放。
- 输入有音频时，输出仍包含音频轨；输入无音频时不报错。
- 输出视频帧数、尺寸和帧率与输入一致。

### 可靠性

- 单元测试覆盖模型错误、候选拒绝、人工确认、SIFT/LK 失败、FFmpeg 缺失、音频映射和任意分支数量。
- 使用当前门店视频和至少一个错误候选做回归测试。
- 通过干净克隆运行 README 中的安装、样片生成和本地启动命令。
- Secret Scan、`git diff --check` 和公开仓库提交检查通过。

## 分阶段范围

第一阶段只实现自动候选验证、来源标记修正、任意分支、音频保留和任务状态。第二阶段再处理多场景切分、前景遮挡和部署。当前阶段不引入 SAM、视频抠像、3D 网格、数据库或云端队列。

## 记录方式

每次模型调用都记录模型名、输入样本哈希、候选数量、验证结论和任务状态，不记录密钥和完整 base64 图片。每个发布版本都必须把产品承诺和实测边界写进 README 与 Demo 脚本。
